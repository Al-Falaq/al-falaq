# qibla

Both geodesies shipped (M2): `QiblaCalculator::default()` is the spherical
fast path, `QiblaCalculator::wgs84()` the WGS84/Karney precise opt-in — see
the `QiblaCalculator` strategies + `tests/Goldens/qibla_*.csv`.

## Pinned inputs

- Kaaba / Makkah: `21.4225241, 39.8261818` (pin `src/alfalak/data/Constants.py:8`).
  Canonical precision is 4 dp (`21.4225, 39.8262`, ~11 m); goldens are tied to
  the exact stored digits — any re-canonicalization invalidates them.
- Mean radius: `6371.0088 km` (IUGG `R1 = (2a+b)/3`, pin `Constants.py:12`).
- Shipped formula: Todhunter p.50 bearing + haversine `atan2` distance
  (pin `src/alfalak/Qibla.py:81-104`).
- Oracle (independent float order, not a tautology): initial-bearing form +
  vector dot-product distance; script gates every run at angular bearing
  diff `≤ 1e-12 deg` / distance diff `≤ 1e-9 km` against `Qibla()`
  (observed maxima on the 23 cities are tighter: `≤ 2.9e-14 deg` /
  `≤ 4.7e-12 km`; the gate keeps ~100x margin for cross-platform float order).
- Goldens: `tests/Goldens/qibla_spherical.csv` (23 cities, 6-dp bearings
  `abs=1e-6`, 3-dp distances `abs=1e-3`); generator: `tools/gen_qibla_spherical.py`.
  The generator writes CSV goldens to stdout (byte-identical to the committed
  file) and diagnostics (pin line, ellipsoidal divergence table, degenerate
  invariants) to stderr; regenerate and diff-review with:
  `PYTHONPATH=<path-to-alfalak-pin>/src python3 tools/gen_qibla_spherical.py > /tmp/qibla_regen.csv`
  then `diff tests/Goldens/qibla_spherical.csv /tmp/qibla_regen.csv`.
  `tests/Goldens/QiblaGoldensTest.php` gates CSV structure (header, 23 rows,
  ranges, precision, source tags, no degenerate rows) plus `magneticHeading`
  vectors and numeric engine parity against the PHP spherical
  implementation (bearings ≤ 1e-6, distances ≤ 1e-3).

## WGS84 / Karney (precise opt-in)

- Entry point: `QiblaCalculator::wgs84()->calculate(Coordinates): QiblaResult`
  — the same `{direction, distanceKm}` shape as `default()`, so switching is a
  one-word change. `default()` remains the default (Todhunter/haversine on the
  IUGG mean radius — cheaper, no series evaluation); `wgs84()` runs the full
  ellipsoidal inverse.
- Engine: `KarneyInverse` (`src/Astro/Services/KarneyInverse.php`, `@internal`)
  is a vendored subset of GeographicLib 2.1's `geodesic.py`/`geomath.py`
  transcribed from the alfalak pin at commit `a7baa8b` (MIT/X11,
  © Charles Karney 2011-2022). Algorithm: C. F. F. Karney, "Algorithms for
  geodesics", *J. Geodesy* 87, 43-55 (2013),
  https://doi.org/10.1007/s00190-012-0578-z.
- WGS84 constants (pin `Geodesy.py:35,38`, defining, exact): `a = 6378137.0 m`
  and `f = 1/298.257223563`. The engine works in metres (`a=6378.137` is the
  km spelling of the same number, not a different value) and converts once at
  the end; derived: `b = a(1-f)`, `e2 = f(2-f)`.
- Iteration caps + tolerances (pin `Geodesy.py:63-70`), transcribed with
  Python's float machinery mapped 1:1: `_MAXIT1 = 20`,
  `_MAXIT2 = _MAXIT1 + mant_dig(53) + 10 = 83` (PHP doubles carry a 53-bit
  mantissa exactly as CPython's `sys.float_info.mant_dig` does, so the cap is
  identical), ladder anchored at `_TOL0 = 2^-52` (`PHP_FLOAT_EPSILON`) with
  `_TOL1 = 200·TOL0` (latitude), `_TOL2 = sqrt(TOL0)` (short-line and
  meridian thresholds), `_TOLB = TOL0` (bisection),
  `_XTHRESH = 1000·TOL2` (astroid-latitude threshold),
  `_TINY = sqrt(PHP_FLOAT_MIN)` (CPython's `sys.float_info.min`, same IEEE 754
  double). Non-convergence past `_MAXIT2` raises `AstronomicalException`;
  there is no silent fallback (PRD §5.3).
- Why Karney and not Vincenty: Vincenty (1975)'s iteration is documented
  non-convergent for nearly-antipodal points, Karney's hybrid Newton/astroid
  iteration converges for all inputs. The proof case is
  `(-20.4, -139.2) → Makkah = 31.740215702° / 19862471.480885 m`, pinned in
  `tests/Astro/KarneyInverseTest.php::testInverseNearAntipodalConverges`
  (the surrounding sweeps additionally gate finiteness, the `(-180, 180]`
  azimuth range, and distance symmetry over antipodal pairs).
- Strategy contract (`Wgs84KarneyCalculator` owns it, not the engine): the
  engine returns the azimuth in `(-180, 180]`; the strategy unwinds to
  `[0, 360)` via `fmod(x, 360) + 360` for negatives, then re-clamps
  `>= 360 → 0.0`. The re-clamp is not cosmetic: `fmod(-1e-15, 360) + 360`
  rounds to exactly `360.0` (`ulp(360) ≈ 5.7e-14`), which `QiblaResult`
  rejects (`testWgs84TinyNegativeAzimuthDoesNotWindTo360` pins it).
  Pin-oracle azimuths are frequently negative — Kuala Lumpur's is
  `-67.557623661` → `292.442376339`. Makkah-self (distance < 1 m) clamps to
  direction `0.0` / distance `0.0`; the raw engine bearing there is
  construction-defined (`180.0`, same construction as the spherical path) and
  never leaks out.
- Goldens: `tests/Goldens/qibla_wgs84.csv` (23 cities, 6-dp bearings /
  3-dp distances, gates ≤ 1e-6° / ≤ 1e-3 km) regenerated by
  `tools/gen_qibla_wgs84.py` against the pin and diff-reviewed
  (`PYTHONPATH=<path-to-alfalak-pin>/src python3 tools/gen_qibla_wgs84.py > /tmp/qibla_wgs84_regen.csv`
  then `diff tests/Goldens/qibla_wgs84.csv /tmp/qibla_wgs84_regen.csv`; the
  committed file is byte-identical). CSV goldens go to stdout, diagnostics
  (pin line, per-city raw engine azimuth/distance, degenerate invariants) go
  to stderr. The Makkah-self and antipode rows are stderr-only — never
  bearing goldens — and are pinned as invariants in
  `tests/Qibla/QiblaCalculatorTest.php` (self → exactly `0.0`/`0.0`, antipode
  finite and > 19000 km). Structure + numeric parity of the wired
  `QiblaCalculator::wgs84()` are gated by
  `tests/Goldens/QiblaGoldensTest.php`.
- Spherical-vs-WGS84 divergence, **measured** over the 23 golden cities (diff
  the two CSVs, or read the spherical generator's ellipsoidal divergence
  table on stderr): max |Δdirection| `0.252273°` at Auckland NZ
  (`-36.8485, 174.7633`), median `≈ 0.10°`; max |Δdistance| `26.275 km` at
  Cape Town, and the largest *relative* gap `0.51%` at Nairobi (short lines
  make relative distance error dominate — Madinah is `0.40%` on 345 km). The
  spread is geometry-dependent rather than a function of distance alone
  (Auckland, the farthest city, has the largest bearing gap; Anchorage, also
  far, one of the smallest), so these are measured ceilings for the sampled
  set, not constants. Practical reading: the spherical default is good to a
  few tenths of a degree and tens of km; the ellipsoid is the opt-in for when
  that matters.

## Degenerate contract (invariants only, never bearing goldens)

- Makkah self: finite bearing in `[0, 360)`, distance `≈ 0`. The shipped
  Todhunter order yields `180.0` by construction (`atan2(0, tiny-negative)`);
  the independent order yields `0.0` — both equally valid, exclude from goldens.
- True antipode `(-21.4225241, -140.1738182)`: finite bearing in `[0, 360)`,
  no raise, no NaN; spherical distance golden `≈ πR ≈ 20015.114 km`
  (meaningful on the sphere; WGS84 differs with no single half-circumference).
  The ellipsoidal reference is `≈ 20003.931 km` (`20003931.458625 m`, the
  engine's value at the antipode, pinned in
  `KarneyInverseTest::testInverseTrueAntipodeNoRaise`). An antipodal pair
  shares a meridian, so that number is the meridional half-circumference —
  the distance is unique but multiple shortest geodesics may reach it, so the
  initial azimuth is non-unique; it is a reference point, not a bearing golden.
- No golden within ~1° of the antipode (hyper-sensitive bearings); test
  invariants only there.
- `Qibla` never raises polar/high-latitude errors (a `PrayerTimes` concern);
  Tromsø `69.65N` is an ordinary golden.
- `magneticHeading(declinationEast)` feeds true-north goldens as
  `unwind(true − declination_east)` (untouched by the spherical oracle).
